## 3. The main algorithmic idea

For a ring of `N` processes, the usual approach is:

### Reduce-Scatter

Each process starts with a buffer of size `count`.

The buffer is conceptually divided into `N` chunks.

In each of `N - 1` steps:

- Each process sends one chunk to the next process in the ring.
- Each process receives one chunk from the previous process.
- The received chunk is reduced into the local chunk.

After reduce-scatter, each process owns the final reduced result for one chunk.

---

### All-Gather

After reduce-scatter, each process has one complete reduced chunk.

In each of `N - 1` steps:

- Each process sends its current chunk to the next process.
- Each process receives a chunk from the previous process.
- The received chunk is placed into the correct position in the output buffer.

After all-gather, every process has the full reduced result.

---

### All-Reduce

The simplest correct implementation is:

```text
All-Reduce = Reduce-Scatter + All-Gather
```

So your `pg_all_reduce()` can internally call:

```c
pg_reduce_scatter(...);
pg_all_gather(...);
```

Or you can combine them into one optimized implementation.

## 7. Eager vs. Rendezvous design

This is probably the most important experimental part.

### Eager protocol

For small messages:

```text
Sender immediately writes data to receiver buffer.
Receiver has pre-posted buffers.
Completion may be signaled using RDMA Write with Immediate.
```

This is simple and low-latency.

Possible design:

```text
Sender:
    RDMA Write data into receiver staging buffer
    Use RDMA Write with Immediate to notify receiver

Receiver:
    Post receive buffer
    Poll completion queue
    Immediate data tells sender identity / step / chunk info
```

Eager is good when message size is small and buffer usage is predictable.

---

### Rendezvous protocol

For large messages:

```text
Sender tells receiver:
    "I have data of size S at address A with key K."

Receiver then decides when and how to receive it.
```

Possible designs:

#### Receiver-initiated RDMA Read

```text
Sender sends control message with remote address and rkey.
Receiver performs RDMA Read from sender buffer.
Receiver completes locally.
```

This is very suitable for zero-copy.

#### Sender-initiated RDMA Write

```text
Receiver sends target address and rkey to sender.
Sender performs RDMA Write directly into receiver buffer.
Sender may use RDMA Write with Immediate for completion notification.
```

Both are valid. The exercise explicitly allows RDMA Write with Immediate for signaling completion.

## 8. Zero-copy requirement

The exercise says:

> Use RDMA Read or RDMA Write for large messages zero copy on the all-gather phase.

This means that for large all-gather messages, you should avoid extra copies if possible.

Instead of:

```text
network -> temporary buffer -> memcpy -> application buffer
```

You want:

```text
network -> application buffer directly
```

To do that, the application buffer must be registered as an RDMA memory region.

For example:

```c
ibv_reg_mr(pd, recvbuf, size, access_flags);
```

Then the remote process can write directly into the correct offset of `recvbuf`, or the local process can read directly into `recvbuf`.

This is an important optimization and should be measured in the final report.

---

## 9. Pipelining requirement

The exercise also asks for pipelining to overlap communication and computation.

For ring collectives, pipelining usually means splitting messages into smaller chunks.

For example, instead of sending one large chunk per step:

```text
Chunk:
[---------------------- large chunk ----------------------]
```

Split it into micro-chunks:

```text
[chunk 0][chunk 1][chunk 2][chunk 3]
```

Then you can overlap:

- Sending micro-chunk `i`
- Reducing or processing micro-chunk `i - 1`
- Receiving micro-chunk `i - 2`

This is similar to software pipelining.

For reduce-scatter:

```text
Step k:
    send next micro-chunk
    receive previous micro-chunk
    reduce previously received micro-chunk
```

For all-gather:

```text
Step k:
    send next micro-chunk
    receive previous micro-chunk
    place received micro-chunk into final buffer
```

The main design question is:

> What should the pipeline chunk size be?

Too small:

- More control overhead
- More completions
- More CPU work

Too large:

- Less overlap
- Higher latency
- More buffering

So you can experiment with different chunk sizes.

## 11. Key design decisions you will need to make

### Decision 1: Use RDMA Write or RDMA Read?

RDMA Write:

- Sender pushes data.
- Sender needs remote address and rkey.
- Can use Write with Immediate to notify receiver.
- Good for eager style.

RDMA Read:

- Receiver pulls data.
- Receiver needs sender address and rkey.
- Good for rendezvous style.
- Often natural for zero-copy large transfers.

You may use both:

```text
Small messages: RDMA Write with Immediate
Large messages: Rendezvous + RDMA Read
```

---

### Decision 2: Use one QP or multiple QPs?

Simplest:

- One QP to next rank
- One QP from previous rank

But you could also use:

- One bidirectional QP between each pair
- Separate QPs for control and data
- Separate QPs for reduce-scatter and all-gather

For a course project, I would start simple:

```text
One QP to next rank.
One QP to previous rank.
```

---

### Decision 3: How to signal completion?

Options:

1. RDMA Write with Immediate
2. RDMA Send after RDMA Write
3. Receiver polls memory flag
4. Receiver uses RDMA Read and local completion

The exercise explicitly mentions:

> One CAN use RDMA Write with Immediate for signalling completion.

So that is probably the cleanest approach.

Important detail:

Even with RDMA Write with Immediate, the receiver usually needs to post a receive work request so that it can receive the immediate notification.

---

### Decision 4: What is the eager threshold?

You need a threshold such as:

```c
if (message_size <= EAGER_MAX)
    eager_protocol();
else
    rendezvous_protocol();
```

You can start with something like:

```text
Eager threshold = 8 KB, 16 KB, 32 KB, or 64 KB
```

Then measure and tune it.

---

### Decision 5: How to handle reduction operations?

The API includes:

```c
DATATYPE datatype;
OPERATION op;
```

You should define enums, for example:

```c
typedef enum {
    PG_INT,
    PG_FLOAT,
    PG_DOUBLE,
    PG_LONG
} DATATYPE;

typedef enum {
    PG_SUM,
    PG_MAX,
    PG_MIN,
    PG_PROD
} OPERATION;
```

At first, implement:

```text
PG_INT + PG_SUM
```

Then extend later.

## 12. Potential difficulties

This project is not extremely difficult conceptually, but it has many practical pitfalls.

### RDMA setup complexity

Verbs require careful initialization.

You need to correctly set:

- Port number
- GID index
- LID
- QP capabilities
- Access flags
- Path MTU
- QP state transitions

A small mistake can make the QP fail.

---

### Completion handling

You need to be careful with:

- Polling completion queue
- Handling errors
- Making sure receive buffers are posted before transfers
- Not overflowing the completion queue
- Ordering of completions

Since the program is single-threaded, you will probably use busy-polling:

```c
while (ibv_poll_cq(cq, 1, &wc) == 0) {
    /* wait */
}
```

That is fine for this project.

---

### Memory registration

RDMA buffers must be registered.

Registration is expensive, so you should not register and deregister memory for every operation.

Better approach:

- Register buffers once during setup, or
- Register user buffers inside each collective call if necessary, but understand the performance cost.

For performance testing, pre-registering buffers is better.

---

### Deadlocks in ring communication

Ring collectives can deadlock if ranks do not post receives in time.

For example:

```text
Rank 0 sends to Rank 1.
Rank 1 has not posted a receive buffer.
Sender waits forever.
```

So you must carefully order:

```text
Post receive
Enable communication
Send data
Poll completion
```

---

### Correctness with pipelining

Pipelining improves performance but makes correctness harder.

You need to ensure:

- A buffer is not reused before its transfer completes.
- Reduction happens on the correct chunk.
- Received chunks are placed in the correct output offset.
- Completions are matched to the right step.

Using tags in immediate data can help.

For example, immediate data can encode:

```text
source rank
step number
chunk number
protocol type
```

# 3. Why pure “eager only for notification” is not enough

The assignment says:

> compare the Rendezvous protocol to a trivial “eager” case.

That means you need a fair comparison where the same collective can run using eager and using rendezvous.

For example, for an all-reduce with message size `M`, you want to compare:

```text
pg_all_reduce(..., EAGER_MODE)
```

against:

```text
pg_all_reduce(..., RENDEZVOUS_MODE)
```

or:

```text
pg_all_reduce(..., AUTO_MODE)
```

If your eager protocol is only used for tiny notifications, then the data path is always rendezvous, and the comparison becomes less meaningful.

So I would implement three modes:

```c
typedef enum {
    PG_PROTOCOL_AUTO,
    PG_PROTOCOL_EAGER,
    PG_PROTOCOL_RENDEZVOUS
} PG_PROTOCOL;
```

Then inside the library:

```c
if (mode == PG_PROTOCOL_EAGER) {
    use eager for data;
} else if (mode == PG_PROTOCOL_RENDEZVOUS) {
    use rendezvous for data;
} else {
    if (message_size <= eager_threshold)
        use eager;
    else
        use rendezvous;
}
```

Control messages can always be eager.

That gives you both:

1. a practical design, and  
2. an experimentally fair comparison.

# 4. What I would use eager for

I would use eager for these cases:

## 4.1 Control messages

Examples:

```text
RTS
CTS
ACK
step notification
chunk-ready notification
barrier token
protocol synchronization
```

These are small and latency-sensitive. Eager is perfect.

Possible implementation:

```text
IBV_WR_SEND
```

or:

```text
IBV_WR_RDMA_WRITE_WITH_IMM
```

The assignment says:

> One CAN use RDMA Write with Immediate for signalling completion.

So `RDMA_WRITE_WITH_IMM` is a very good fit for notifications.

For example:

```text

Sender uses RDMA_WRITE_WITH_IMM.
Immediate data encodes:
    source rank
    phase
    step
    chunk id
    message type
```

The receiver gets a completion and knows what arrived.

## 4.2 Small data updates

For small reduce-scatter chunks or small all-gather chunks, eager is also good.

Example:

```text
chunk size <= 4 KB
```

or:

```text
chunk size <= 8 KB
```

The exact threshold should be measured, not guessed.

For small messages, eager usually wins because it avoids extra handshake round trips.

Eager large data can be dangerous because the receiver must already have buffers ready. But for small messages, this is usually acceptable.

# 5. What I would use rendezvous for

I would use rendezvous for bulk data movement.

Especially for:

```text
large reduce-scatter chunks
large all-gather chunks
large all-reduce messages
zero-copy transfers
```

Rendezvous is useful because the receiver can control when and where the large data lands.

This is especially important for zero-copy.

For example:

```text
Sender:
    I have chunk X ready at address A with rkey K.

Receiver:
    Read it directly into my final recvbuf at offset Y.
```

Or:

```text
Receiver:
    Here is my target address B and rkey R.
    Write directly there.
```

That avoids extra copies.

# 6. Recommended protocol design

I would implement the following.

## Eager protocol

For small data or control:

```text
Sender:
    RDMA_WRITE data into receiver pre-posted buffer
    or RDMA_WRITE_WITH_IMM if payload is small

Receiver:
    has already posted receive buffers
    polls CQ
    immediate data tells it what arrived
```

For small messages, you can even put the whole payload inside immediate data if it fits, but usually it is simpler to write into a small registered receiver buffer.

The important point is:

```text
Sender does not wait for permission.
```

That is the eager idea.

---

## Rendezvous protocol

For large data, I would implement one of these two variants.

---

## Variant A: Receiver-initiated RDMA Read

This is a classic rendezvous design.

Flow:

```text
Sender:
    prepare source buffer
    register source buffer if needed
    send RTS control message:
        source address
        rkey
        size
        chunk id
        phase
        step

Receiver:
    receives RTS
    chooses final destination buffer
    posts RDMA_READ from sender buffer into local destination
    polls RDMA_READ completion
    optionally sends ACK back to sender
```

This is very good for zero-copy because the receiver can read directly into `recvbuf`.

Example in all-gather:

```text
Rank i receives RTS from rank i-1.
Rank i performs RDMA_READ:
    source = rank i-1's chunk
    destination = recvbuf[origin_rank]
```

Then no intermediate copy is needed.

This is probably the cleanest rendezvous design for your assignment.

---

## Variant B: Sender-initiated RDMA Write

Flow:

```text
Sender:
    sends RTS:
        chunk id
        size
        step

Receiver:
    sends CTS:
        destination address
        rkey

Sender:
    RDMA_WRITE data directly into receiver's destination buffer
    optionally uses RDMA_WRITE_WITH_IMM for completion notification
```

This is also valid.

The assignment explicitly says you may use:

```text
RDMA Write with Immediate for signalling completion
```

So this variant matches that hint nicely.

---

## Which variant should you choose?

I would probably choose:

```text
Rendezvous large data:
    receiver-initiated RDMA_READ
```

and:

```text
Control/notification:
    eager SEND or RDMA_WRITE_WITH_IMM
```

Why?

Because RDMA_READ gives the receiver control over the final destination, which is ideal for zero-copy all-gather.

But if you want to use `RDMA_WRITE_WITH_IMM` more directly, then use sender-initiated rendezvous with CTS.

Both are reasonable.

# 7. How this affects the ring collectives

## Reduce-Scatter

Reduce-scatter requires reduction, so zero-copy is harder.

You usually need a staging buffer:

```text
receive chunk from previous rank into staging buffer
reduce staging buffer into local chunk
send updated chunk to next rank
```

For large chunks, rendezvous can be used to transfer the chunk into the staging buffer.

So reduce-scatter could look like:

```text
for step = 0 to N-2:
    send chunk to next rank
    receive chunk from previous rank
    reduce received chunk into local chunk
```

If chunk is small:

```text
eager transfer into staging buffer
```

If chunk is large:

```text
rendezvous transfer into staging buffer
```

---

## All-Gather

All-gather is where zero-copy matters most.

For large chunks, you want:

```text
network buffer -> final recvbuf
```

not:

```text
network buffer -> temporary buffer -> memcpy -> final recvbuf
```

So for all-gather, rendezvous can place the incoming chunk directly into the correct offset of `recvbuf`.

Example:

```text
recvbuf[origin_rank * chunk_size ...]
```

If using RDMA_READ:

```text
Rank i reads chunk from previous rank directly into:
    recvbuf + origin_rank * chunk_size
```

If using RDMA_WRITE:

```text
Previous rank writes chunk directly into:
    rank i's recvbuf + origin_rank * chunk_size
```

This satisfies the assignment requirement:

> Use RDMA Read or RDMA Write for large messages zero copy on the all-gather phase.

### ASSISTANT
Yes — **RDMA Write can help a lot with pipelining**, but it helps only if you design the buffering and flow control correctly.

The important point is:

> RDMA Write by itself does not automatically create a good pipeline.  
> Pipelining comes from having multiple buffers/slots, overlapping sends/receives/computation, and keeping the send queue busy.  
> RDMA Write is a very good primitive for implementing that kind of sender-driven pipeline.

---

## 1. Why RDMA Write helps pipelining

With RDMA Write, the sender can push data as soon as it is ready:

```text
Rank i:
    chunk 0 ready -> RDMA_WRITE to rank i+1
    chunk 1 ready -> RDMA_WRITE to rank i+1
    chunk 2 ready -> RDMA_WRITE to rank i+1
```

The sender does not need to wait for the receiver to issue a read for every chunk, assuming the receiver has already exposed valid target addresses.

This is useful for pipelining because you can keep multiple transfers in flight:

```text
time -->

send chunk 0       send chunk 1       send chunk 2
             reduce chunk 0      reduce chunk 1
```

or, more generally:

```text
communication:
    [write chunk k] [write chunk k+1] [write chunk k+2]

computation:
                  [reduce chunk k-1] [reduce chunk k]
```

So RDMA Write is a good fit for a **push-based pipeline**.

---

## 2. RDMA Write vs RDMA Read for pipelining

### RDMA Write

RDMA Write is sender-initiated:

```text
Sender writes into remote buffer.
```

This is good when:

- the sender knows the remote target address,
- the receiver has pre-registered buffers,
- the sender wants to push data aggressively,
- you want to keep the send queue full.

For a ring collective, this can be very useful:

```text
rank i knows:
    next rank's recvbuf address
    next rank's rkey
    correct offset for the chunk
```

Then rank `i` can write directly into rank `i+1`'s final buffer.

This is especially helpful in all-gather.

---

### RDMA Read

RDMA Read is receiver-initiated:

```text
Receiver pulls data from sender.
```

This is good when:

- the receiver wants full control over the destination buffer,
- you want zero-copy directly into a local application buffer,
- you want the receiver to decide when to start each transfer.

But for pipelining, RDMA Read can add an extra dependency:

```text
Receiver must know that sender data is ready.
Receiver posts RDMA_READ.
Receiver waits for local completion.
```

You can still pipeline RDMA Read by posting multiple reads, but the receiver drives the pipeline.

---

## 3. For pipeline optimization, RDMA Write is often easier

For your ring all-reduce project, I would say:

```text
RDMA Write is usually easier for pipelining the all-gather phase.
RDMA Read is useful for receiver-controlled rendezvous zero-copy.
```

Why?

Because in a ring all-gather, the sender often already knows where the chunk should go on the next rank.

For example, rank `i` sends a chunk belonging to origin rank `r`.

The next rank should place that chunk at:

```text
recvbuf + r * chunk_size
```

If rank `i` already knows:

```text
next_rank_recvbuf_base
next_rank_rkey
```

then it can directly do:

```text
RDMA_WRITE to next_rank_recvbuf_base + r * chunk_size
```

That is zero-copy and pipeline-friendly.

## 4. How RDMA Write helps the pipeline in all-gather

Suppose each logical chunk is split into micro-chunks for pipelining.

Without pipeline:

```text
send whole chunk
wait
receive whole chunk
wait
process
```

With pipeline and RDMA Write:

```text
sender:
    RDMA_WRITE micro-chunk 0
    RDMA_WRITE micro-chunk 1
    RDMA_WRITE micro-chunk 2
    ...

receiver:
    process micro-chunk 0 when notified
    process micro-chunk 1 when notified
    process micro-chunk 2 when notified
```

The sender can keep several micro-chunks in flight.

This is similar in spirit to your previous `bw.c` benchmark, where you had:

```text

SIGNAL_INTERVAL = 64
```

and you kept many RDMA WRITEs outstanding to maximize throughput.

For the ring project, the idea is similar, but instead of one unidirectional stream to one server, you have ring neighbors and collective phases.

## 5. Use RDMA Write with Immediate for pipeline notifications

For pipelining, the receiver needs to know:

```text
Which micro-chunk arrived?
Which phase does it belong to?
Which step?
Which origin rank?
Is it safe to process it?
```

`RDMA_WRITE_WITH_IMM` is useful here.

Example:

```text
Sender:
    RDMA_WRITE data into next rank's buffer
    immediate data = encoded metadata

Receiver:
    gets completion
    decodes immediate data
    knows exactly which pipeline slot arrived
```

Immediate data could encode:

```text
phase
step
chunk id
micro-chunk id
```

For example:

```c
imm_data =
    (phase << 24) |
    (step << 16) |
    (chunk << 8) |
    (microchunk);
```

This allows the receiver to process pipeline chunks in the right order.

## 6. But you need flow control

RDMA Write can be dangerous for pipelining if the receiver has a limited number of buffers.

If the sender writes too fast, it may overwrite data that the receiver has not processed yet.

So you need one of these designs.

---

### Option A: Unique final slots, no reuse

For all-gather, each chunk has a final destination slot:

```text
recvbuf[origin_rank]
```

If every chunk goes to a unique final location, then the sender can write without worrying about overwriting a previous chunk.

This is very good for pipelining.

Example:

```text
chunk from rank 0 -> recvbuf[0]
chunk from rank 1 -> recvbuf[1]
chunk from rank 2 -> recvbuf[2]
chunk from rank 3 -> recvbuf[3]
```

No slot is reused during the all-gather phase.

This makes RDMA Write very attractive for all-gather.

---

### Option B: Pipeline slots with credits

For reduce-scatter, you may use staging buffers:

```text
slot 0
slot 1
slot 2
slot 3
```

These slots are reused.

Then you need flow control.

Example:

```text
Receiver gives sender P credits.
Sender may have at most P outstanding writes.
When receiver finishes processing a slot, it returns one credit.
```

This gives you a classic pipeline:

```text
P = 3

sender:
    write to slot 0
    write to slot 1
    write to slot 2
    wait for credit
    write to slot 0 again
```

The pipeline depth `P` controls overlap.

If `P = 1`, no pipeline.

If `P = 2` or `P = 3`, you can overlap communication and computation.

If `P` is too large, you waste memory and may increase complexity.

---

## 7. Write helps if you use batching and selective signaling

Your previous `bw.c` code already used an important optimization:

```text
Post many WRs in a linked list.
Signal only every K-th WR.
```

That idea can also help the ring project.

For pipeline performance, you do not necessarily need one completion per tiny transfer.

For example:

```text
micro-chunk 0: unsignaled RDMA_WRITE
micro-chunk 1: unsignaled RDMA_WRITE
micro-chunk 2: unsignaled RDMA_WRITE
micro-chunk 3: signaled RDMA_WRITE
```

Then one completion tells you that a batch is done.

But there is a tradeoff:

```text
Too many notifications:
    high CPU/CQ overhead

Too few notifications:
    less fine-grained overlap
```

So the best pipeline chunk size and signaling granularity should be measured.

---

## 8. Write with Immediate has overhead

`RDMA_WRITE_WITH_IMM` is convenient, but it has cost.

Every immediate write usually consumes a posted receive on the receiver and creates a completion event.

If you use it for very small micro-chunks, the notification overhead may dominate.

So you should tune the pipeline chunk size.

For example, instead of:

```text
1 KB micro-chunk + immediate notification
```

maybe this is better:

```text
64 KB micro-chunk + immediate notification
```

or:

```text
256 KB micro-chunk + immediate notification
```

The best value depends on the hardware and message size.

---

## 9. Where Write is especially useful

I would use RDMA Write especially in these places:

### Control/notification messages

Small eager control messages:

```text
RTS
CTS
ACK
chunk ready
step done
```

Can be sent eagerly.

---

### Small data updates

Small chunks:

```text
chunk_size <= eager_threshold
```

can use eager RDMA Write.

---

### All-gather bulk phase

Large all-gather chunks can use RDMA Write directly into the next rank’s final `recvbuf`.

This satisfies the zero-copy requirement:

```text
RDMA_WRITE -> final recvbuf
```

No intermediate copy needed.

---

### Pipelined bulk transfer

For pipeline:

```text
split chunk into micro-chunks
RDMA_WRITE each micro-chunk into correct remote slot/offset
notify with immediate data or batched control message
```

This is where Write really helps.

---

## 10. Where Read may still be useful

RDMA Read is still useful for rendezvous.

For example:

```text
Sender:
    large source buffer ready
    sends RTS with addr/rkey

Receiver:
    performs RDMA_READ directly into final buffer
```

This gives the receiver full control.

It is also zero-copy.

But for a highly aggressive pipeline, receiver-driven Read can be slightly less convenient because the receiver must keep issuing reads.

That said, it can still be pipelined:

```text
receiver:
    post RDMA_READ for micro-chunk 0
    post RDMA_READ for micro-chunk 1
    post RDMA_READ for micro-chunk 2
```

So Read can also pipeline. The difference is mostly about who drives the pipeline.

## 3. Pipeline remainder

You correctly pointed out:

> we need to think about the remainder.

There are actually two remainder problems.

---

### Remainder problem 1: splitting among ranks

If the total number of elements is not divisible by the number of processes, the ring segments cannot all have the same size.

Example:

```text
count = 10
size = 4
```

Then we cannot give every rank exactly `10 / 4 = 2.5` elements.

A common solution is block distribution:

```text
base = count / size
rem  = count % size

first rem ranks get base + 1 elements
remaining ranks get base elements
```

For `count = 10`, `size = 4`:

```text
rank 0 segment size = 3
rank 1 segment size = 3
rank 2 segment size = 2
rank 3 segment size = 2
```

This works, but the ring algorithm becomes slightly more complicated because each rank must know the segment offsets and sizes of all ranks.

---

### Remainder problem 2: pipeline micro-chunks

Even if each rank segment is known, we still split it into pipeline micro-chunks.

Example:

```text
segment size = 1000 KB
pipeline chunk = 256 KB
```

Then:

```text
chunk 0 = 256 KB
chunk 1 = 256 KB
chunk 2 = 256 KB
chunk 3 = 232 KB   <-- remainder
```

The last micro-chunk can simply be smaller.

So the pipeline logic should be:

```text
while remaining_bytes > 0:
    this_chunk = min(pipeline_chunk_size, remaining_bytes)
    send/receive/reduce this_chunk
    remaining_bytes -= this_chunk
```

For the first bring-up version, it is reasonable to require:

```text
count % size == 0
```

and maybe also:

```text
segment_bytes % pipeline_chunk_size == 0
```

Then, after the simple version works, we generalize to arbitrary remainders.

---

## 4. Reduce-Scatter buffer options, elaborated

You asked for more detail on the Reduce-Scatter buffer options.

Reduce-Scatter is the harder phase because it involves computation.

The ring algorithm needs a working buffer of the full message size. Each rank starts with its own contribution, then repeatedly receives a chunk from the previous rank, reduces it into the local working chunk, and forwards the updated chunk.

The problem is: **where should incoming RDMA data land?**

---

### Option A: dedicated internal staging/work buffer

The library allocates internal buffers.

For example:

```text
work_buf:
    full-size buffer used for the reduction algorithm

stage_buf:
    one or more pipeline slots where incoming network chunks land
```

Flow:

```text
1. copy user sendbuf into work_buf
2. register work_buf and stage_buf
3. incoming chunk from previous rank lands in stage_buf
4. CPU reduces stage_buf into the correct part of work_buf
5. updated chunk from work_buf is sent to next rank
6. after reduce-scatter, copy the owned final segment into user recvbuf
```

Pros:

- safe
- user `sendbuf` is not modified
- user `recvbuf` is not overwritten prematurely
- much easier to pipeline
- easy to protect buffers from being overwritten while RDMA is still reading them
- clean separation between network buffers and reduction buffers

Cons:

- extra copy from `sendbuf` into `work_buf`
- extra copy from final reduced segment into `recvbuf`
- more memory registration

But this is the cleanest design.

---

### Option B: use user buffers directly / in-place

This means using the user’s `sendbuf` or `recvbuf` as the working buffer.

For example:

```text
copy nothing
use sendbuf as the reduction workspace
modify sendbuf in-place
```

or:

```text
write incoming chunks directly into recvbuf
reduce in-place inside recvbuf
```

Pros:

- fewer copies
- potentially better performance

Cons:

- may modify `sendbuf`, which is usually supposed to be input
- `recvbuf` may be too small for the full reduce-scatter working state
- much harder to pipeline safely
- risk that RDMA reads a buffer while CPU is modifying it
- harder to maintain correctness if the same buffer is used for input, temporary reduction, and output

This is more aggressive and more error-prone.

---

### My recommendation

For this project, I strongly recommend:

```text
Option A: internal work buffer + internal staging buffer
```

It is much easier to make correct, and the assignment’s zero-copy requirement is specifically for the **all-gather phase**, not necessarily for reduce-scatter.

---

## 5. Will RDMA Write ordering be a problem for barriers?

You asked:

> because writing the data doesn't happen before the receiver acknowledges it, will it be a problem?

It can be a problem **if** we send a “phase done” or barrier message before the RDMA Writes are actually complete.

So we need a rule:

```text
Do not send a phase-done / barrier / data-ready SEND
until all RDMA WRITEs for that phase are locally complete.
```

For RC QPs, a local completion for an RDMA Write generally means the write has been delivered and acknowledged by the remote side’s transport. But the receiver’s CPU still does not know that the data arrived unless we notify it.

So the safe pattern is:

```text
Sender:
    post RDMA_WRITEs
    wait for local completion of the final outstanding RDMA_WRITE
    post SEND("data done" or "phase done")

Receiver:
    receives SEND
    now knows the RDMA data is safe to process
```

For rendezvous:

```text
Sender:
    SEND RTS

Receiver:
    SEND CTS with target address/rkey

Sender:
    RDMA_WRITE payload
    wait for local RDMA_WRITE completion
    SEND DATA_DONE

Receiver:
    receives DATA_DONE
    processes payload
```

The CTS is **permission to write**, not proof that data has arrived.

So no, it is not a problem as long as we enforce this ordering rule.

## 2. Same total size does not remove the remainder problem

You said:

> for the first problem - all machines know the size because all have the same data size.

That is true: every rank knows the same `count`, so every rank can compute the same logical layout.

But the remainder problem still exists if:

```text
count % size != 0
```

Example:

```text
count = 10
size = 4
```

All ranks know `count = 10`, but the ring cannot split 10 elements into 4 equal contiguous segments.

A normal block distribution would be:

```text
rank 0: 3 elements
rank 1: 3 elements
rank 2: 2 elements
rank 3: 2 elements
```

So the issue is not that ranks disagree about the size. The issue is that the logical segments may have different sizes.

For the first working version, I still recommend requiring:

```text
count % size == 0
```

Then later we can add the general case.

## 3. Your “always send 1 MB packets” idea is okay as pipelining, but not as the ring segmentation

You suggested:

> what about not dividing but always sending for example 1 MB each packet and when we finish sending all we send the remainder

That is a good way to pipeline the **data movement**, but the ring algorithm still needs logical ownership of chunks.

For ring all-reduce, the data is conceptually divided into `size` segments:

```text
segment 0 belongs to rank 0 in reduce-scatter
segment 1 belongs to rank 1
segment 2 belongs to rank 2
segment 3 belongs to rank 3
```

During reduce-scatter, each rank is responsible for fully reducing one segment.

During all-gather, each rank must receive all segments and place them in the correct location.

So we need both:

```text
logical segmentation:
    divide buffer into size ring segments

pipeline packetization:
    divide each segment into smaller pipeline packets
```

For example:

```text
total message = 10 MB
size = 4
segment size = 2.5 MB
pipeline packet size = 1 MB
```

Then each segment is transferred as:

```text
packet 0: 1 MB
packet 1: 1 MB
packet 2: 0.5 MB   <-- remainder
```

That is clean.

If instead we try to send a global stream of 1 MB packets without segment boundaries, we would need extra metadata to figure out which part of each packet belongs to which logical segment. It is possible, but more complicated and probably not worth it.

So the clean design is:

```text
First divide by ranks.
Then divide each rank segment into fixed-size pipeline packets.
The last packet of a segment may be smaller.
```

## 4. Zero-copy and Reduce-Scatter

You said:

> for 4. I’m still not sure because I aspire for the best performance. and I think I want zero copy wherever we can.

That is a good goal, but we need to be precise about what zero-copy means in each phase.

---

### All-Gather can be truly zero-copy

For large all-gather messages, we can use RDMA Write directly into the final `recvbuf`:

```text
RDMA_WRITE -> user recvbuf
```

No intermediate buffer. That satisfies the assignment requirement.

---

### Reduce-Scatter cannot be fully zero-copy because reduction needs CPU

In reduce-scatter, incoming data must be reduced with local data:

```text
received chunk + local chunk -> reduced chunk
```

RDMA Write or RDMA Read can move the incoming chunk without CPU copying, but the reduction itself requires the CPU to read the received chunk and write the reduced result.

So the best we can do in reduce-scatter is:

```text
network -> registered staging buffer       [zero-copy DMA]
staging buffer -> reduction -> work buffer [CPU reduction]
```

The network transfer can be zero-copy, but the reduction step cannot be avoided.

---

### The big performance question: can we modify `sendbuf`?

There are two main designs.

---

### Safe design: internal work buffer

```text
1. register user sendbuf and recvbuf
2. allocate internal work buffer
3. copy sendbuf into work buffer
4. use work buffer for ring reduce-scatter
5. incoming chunks land in internal staging slots
6. CPU reduces staging slots into work buffer
7. final owned segment is copied into recvbuf
```

Pros:

- safe
- `sendbuf` is not modified
- matches normal collective semantics
- easier to reason about

Cons:

- one extra copy from `sendbuf` into `work_buf`
- slightly lower performance

---

### Performance design: use `sendbuf` as the work buffer

```text
1. register user sendbuf and recvbuf
2. use sendbuf itself as the reduce-scatter work buffer
3. incoming chunks land in internal staging slots
4. CPU reduces staging slots directly into sendbuf
5. final owned segment is copied into recvbuf
```

Pros:

- avoids the initial `sendbuf -> work_buf` copy
- better performance
- more zero-copy-friendly

Cons:

- modifies `sendbuf`
- may violate expected collective semantics
- risky if tests expect `sendbuf` to remain unchanged

---

### Best practical solution

I think the best solution is:

```text
Implement both, selected by a compile-time flag.
```

For example:

```text
SAFE_MODE:
    internal work buffer

INPLACE_MODE:
    use sendbuf as work buffer
```

Then we can default to safe mode for correctness, and benchmark inplace mode for maximum performance.

## 2. Why eager receive buffering needs one correction

You said:

> 1.A I think - all is known before we start the ring, or maybe B because we need one send per packet.

This is exactly the right concern.

With eager `SEND`:

```text
one eager packet = one SEND
one eager packet consumes one posted RECV
```

So the receiver must have a receive buffer posted.

In your `bw.c`, the control receive pool was:

```text
32 receives posted once
never refreshed
```

That worked because the total number of control messages was known and small:

```text
21 sizes -> 21 done/ack messages
32 receives are enough
```

But in the ring project, the number of eager data packets can be much larger. If we use a fixed pool and never refresh it, we will eventually run out of posted receives.

So there are three possible strategies.

---

### Strategy A: huge pre-posted pool for all eager packets

```text
Before the collective:
    calculate total number of eager packets
    post one RECV per packet
```

Pros:

- simple logic
- no reposting during the collective

Cons:

- may require many receive buffers
- wastes memory
- bad if message size or packet count is large

This is the “all is known before we start” idea, but it can become expensive.

---

### Strategy B: bounded pool with reposting

```text
Before the collective:
    post P eager receive buffers

During the collective:
    when an eager RECV completes,
    process the packet,
    then repost that buffer
```

Pros:

- memory bounded
- works for arbitrary number of packets
- standard high-performance pattern
- matches pipelining

Cons:

- slightly more logic than a never-refreshed pool
- sender may temporarily outrun receiver and trigger RNR if not paced well

This is probably the best practical design.

---

### Strategy C: synchronous per-packet posting

```text
For each step:
    post one RECV for the expected packet
    post one SEND
    poll for completions
```

Pros:

- very simple
- no large pool

Cons:

- more likely to hit RNR if the sender sends before the receiver posts
- less pipelining
- lower performance

This is acceptable for first bring-up, but not ideal for the final benchmark.

---

## 3. My corrected recommendation for eager receives

I would not use a huge one-time pool unless the total number of eager packets is tiny.

I would use:

```text
bounded eager receive pool + reposting
```

For example:

```text
PG_EAGER_POOL_DEPTH = 16
```

Each eager receive buffer could be sized to:

```text
PG_EAGER_THRESHOLD
```

or to the maximum eager packet size.

When a receive completes:

```text
handle packet
repost the same buffer
```

This gives us bounded memory and supports many packets.

## Why I recommended one shared CQ

It is not because one CQ is the only possible design. It is because this project is:

```text
single-threaded
two QPs per rank
busy-polling
```

With one shared CQ:

```text
Rank has:
    qp_to_next
    qp_from_prev

Both QP send completions and receive completions go to one CQ.

Main loop:
    poll one CQ
    dispatch completion based on wr_id
```

This gives one place to poll and one completion dispatch loop.

With separate CQs:

```text
qp_to_next   -> cq_to_next
qp_from_prev -> cq_from_prev
```

or:

```text
send completions -> send CQ
recv completions -> recv CQ
```

the single-threaded program still has to poll all relevant CQs anyway:

```text
poll cq_to_next
poll cq_from_prev
process completions
```

So separate CQs can make the code more complex without giving much benefit here.

---

## When separate CQs are useful

Separate CQs are useful if:

```text
you have multiple polling threads
you use completion channels/events
you want strict isolation between completion classes
you are worried about one CQ becoming a bottleneck
```

But for this course project, those are not major concerns.

---

## Important point: shared CQ does not break QP ordering

RDMA ordering is per QP.

If both QPs share one CQ, completions from the two QPs may interleave in the CQ:

```text
completion from qp_to_next
completion from qp_from_prev
completion from qp_to_next
completion from qp_from_prev
```

That is fine.

For each individual QP, completions still appear in RC order. The `wr_id` tells us which QP and which operation completed.

Example encoding:

```text
wr_id =
    QP identifier
    completion class
    buffer slot, if needed
```

So a shared CQ is mainly a simplicity choice.

## Receiving while reducing: how it works

Even though the program is single-threaded, the NIC can still receive data while the CPU is reducing previously received data.

RDMA Write is offloaded to the NIC:

```text
CPU:
    reduces micro-chunk k

NIC:
    writes micro-chunk k+1 into another staging slot
```

The CPU does not need to be actively copying the network data. It only needs to poll completions and process them.

With multiple staging slots, the timeline can look like this:

```text
NIC:
    RDMA_WRITE micro-chunk 0 into slot 0
    RDMA_WRITE micro-chunk 1 into slot 1
    RDMA_WRITE micro-chunk 2 into slot 2
    RDMA_WRITE micro-chunk 3 into slot 3

CPU:
                        reduce micro-chunk 0
                                             reduce micro-chunk 1
                                                                  reduce micro-chunk 2
```

The important design points are:

```text
1. Receiver has multiple staging slots.
2. Sender may write into a slot only after the receiver grants it.
3. Sender sends DATA_DONE per micro-chunk.
4. Receiver reduces a completed micro-chunk.
5. Receiver re-grants that slot so the sender can use it again.
```

That gives overlap between:

```text
network reception
RDMA Write into staging
CPU reduction
```

So your instinct is correct: we should design Reduce-Scatter specifically to allow receiving later micro-chunks while reducing earlier ones.

All-Gather is different. It does not require reduction, so the main goal there is zero-copy into the final `recvbuf` and keeping the RDMA Write pipeline full.

Your idea is:

> when we are ready for a segment, allocate memory for every expected micro-chunk to save CPU, and allow the network to continue even if the CPU is in the middle of reducing a chunk.

That is a good performance-oriented direction.

It changes Reduce-Scatter staging from this:

```text
small pool of reusable staging slots
receiver grants one slot at a time
sender waits for slot credits
receiver reduces one slot, then re-grants it
```

to this:

```text
one contiguous staging buffer large enough for the whole incoming segment
receiver grants the whole segment staging region once
sender writes each micro-chunk into the correct offset
receiver reduces micro-chunks as their DATA_DONE notifications arrive
network can keep filling later micro-chunks while CPU reduces earlier ones
```

This is simpler for the protocol and better for overlap inside a segment.

Important detail: we should **not allocate a separate buffer for every micro-chunk**. That would add allocation overhead and registration overhead.

Instead, we should allocate one contiguous segment-sized staging buffer:

```text
segment staging buffer:

    micro 0   micro 1   micro 2   ...   micro N-1
    [       ][       ][       ] ... [           ]
```

Then each micro-chunk’s offset is just:

```text
offset = micro_index * pipeline_chunk_size
```

The last micro-chunk may be smaller.

This gives the benefit you want without per-micro allocation cost.

---

## Tradeoff

The main tradeoff is memory.

With a slot pool:

```text
memory ≈ PG_RENDEZVOUS_SLOTS * PG_PIPELINE_CHUNK
example: 4 * 256 KiB = 1 MiB
```

With full-segment staging:

```text
memory ≈ segment_size
segment_size = total_message_size / size
```

Example:

```text
total message = 1 GiB
size = 4
segment_size = 256 MiB
```

That is much larger, but still reasonable for many course-node workloads.

For the first performance-oriented design, I think full-segment staging is acceptable. If memory becomes a problem later, we can add a fallback or a maximum staging size.

## 1. Warmup must not contaminate the timed region

Your concern is correct.

A bad benchmark would do this:

```text
start clock
warmup call
timed calls
stop clock
```

That would include warmup, registration, first-time cache effects, and other setup costs.

The correct structure is:

```text
setup buffers
connect process group

warmup call using the same buffers and same count
wait for all ranks to finish warmup

for each timed iteration:
    synchronize ranks
    start clock
    timed collective call
    stop clock
    store time
    synchronize ranks

report min / median / avg
```

The important rules are:

```text
1. Warmup happens before any timed clock starts.
2. Warmup uses the same buffers, count, datatype, and operation.
3. Warmup primes the MR cache and internal buffer cache.
4. A barrier separates warmup from the timed region.
5. Timed iterations are measured only after the start barrier.
6. End synchronization is outside the timed interval, unless we explicitly want to measure global completion.
```

We still need to decide the exact timing protocol, especially whether the timed interval stops at local API return or at a global barrier. I’ll ask that in the next round.

# Consolidated shared understanding

## 1. Project scope

The project is a final RDMA ring collective-communication project.

```text
Language:
    C/C++

Threading:
    single-threaded

API:
    Verbs API

Topology:
    ring

Process counts:
    at least 2
    test with 2 and 4

Main required API:
    connect_process_group()
    pg_all_reduce()
    pg_close()

Additional public collectives:
    pg_reduce_scatter()
    pg_all_gather()
```

The assignment asks for:

```text
1. Compare rendezvous protocol against eager protocol.
2. Implement pipelining to overlap communication and computation.
3. Use RDMA Read or RDMA Write for large-message zero-copy in the all-gather phase.
```

Important assignment detail:

```text
The line about RDMA Write with Immediate was crossed out.
Therefore we will not use RDMA_WRITE_WITH_IMM.
Control and completion signaling will use normal IBV_WR_SEND.
```

## 2. No MPI

MPI will not be used.

Bootstrap and rank establishment are done from the command line and TCP.

## 3. Command-line semantics

Program invocation example:

```bash
test -myindex 03 -list mlxstud01 mlxstud02 mlxstud03 mlxstud04
```

Meaning:

```text
-myindex is 1-based.

rank = atoi(myindex) - 1

For -myindex 03:
    rank = 2

size = number of hostnames in -list

For the example:
    size = 4

list[0] = mlxstud01
list[1] = mlxstud02
list[2] = mlxstud03
list[3] = mlxstud04

prev_rank = (rank - 1 + size) % size
next_rank = (rank + 1) % size
```

For `-myindex 03`:

```text
rank       = 2
prev_rank  = 1
next_rank  = 3
local host = mlxstud03
```

## 4. `servername` handling

The public API is:

```c
int connect_process_group(char *servername, void **pg_handle);
```

But the command line already contains the process list and index.

Settled design:

```text
main() parses -myindex and -list.
main() stores the parsed arguments in a global pg_args structure.
main() calls:

    connect_process_group(list[rank], &pg_handle);

connect_process_group() reads the global pg_args.
connect_process_group() verifies:

    servername == list[rank]

If servername does not match list[rank]:
    return PG_ERR_INVAL
```

So for:

```bash
test -myindex 03 -list mlxstud01 mlxstud02 mlxstud03 mlxstud04
```

the expected servername is:

```text
mlxstud03
```

There is no central bootstrap server.

`servername` is used only as a validation/sanity parameter.

## 5. TCP bootstrap

The bootstrap is:

```text
ring-only
edge-ordered
no identity exchange
binary fixed-size metadata
```

Each rank listens on:

```text
PG_TCP_BASE_PORT + rank
```

Default:

```text
PG_TCP_BASE_PORT = 19000
```

Bootstrap sequence:

```text
All ranks:
    parse command line
    compute rank, size, prev, next
    create listening socket on PG_TCP_BASE_PORT + rank

    for edge = 0 to size - 1:
        sender   = edge
        receiver = (edge + 1) % size

        if I am sender:
            connect to receiver's listening port
            exchange metadata as sender side of edge sender -> receiver

        else if I am receiver:
            accept one incoming connection
            exchange metadata as receiver side of edge sender -> receiver

        else:
            idle during this edge

    close listener
```

This edge-ordered sequence avoids deadlock.

TCP metadata structure:

```c
struct pg_tcp_qp_info {
    uint32_t qpn;
    uint32_t psn;
    uint16_t lid;
    uint16_t reserved;
};
```

Exchange rule for each edge:

```text
client/sender side:
    write pg_tcp_qp_info for its sender-side QP
    read  pg_tcp_qp_info for the receiver-side QP
    write ready tag

server/receiver side:
    read  pg_tcp_qp_info for the sender-side QP
    write pg_tcp_qp_info for its receiver-side QP
    read  ready tag
```

Ready tag:

```text
PG_TCP_READY_TAG = 0x52454144
```

TCP retry behavior:

```text
PG_TCP_RETRY_MS    = 100
PG_TCP_TIMEOUT_SEC = 30
```

TCP bootstrap exchanges only QP metadata:

```text
qpn
psn
lid
```

It does not exchange buffer addresses or rkeys.

Buffer addresses and rkeys are exchanged later during collectives using rendezvous control messages.

## 6. RDMA resources

Assumptions:

```text
InfiniBand only
LID-based addressing
No RoCE/GID support in the first version
```

Reuse the course-hardware assumptions from `bw.c`:

```text
first IB device
IB_PORT = 1
path MTU = port active MTU
pkey_index = 0
min_rnr_timer = 12
timeout = 14
retry_cnt = 7
rnr_retry = 7
max_rd_atomic = 1
max_dest_rd_atomic = 1
```

Each rank creates:

```text
one PD
one shared CQ
two RC QPs:
    qp_to_next
    qp_from_prev
```

QP access flags:

```text
IBV_ACCESS_REMOTE_WRITE only
```

If RDMA Read is ever added later, QP access flags must be reopened.

Inline behavior:

```text
Attempt max_inline_data like bw.c.
Step down declared max_inline_data until QP creation succeeds.
Use the read-back max_inline_data at runtime.
Control SENDs use IBV_SEND_INLINE when they fit.
Otherwise stage them in a registered control buffer.
```

## 7. Completion queue and `wr_id`

Both QPs share one CQ.

Completion identity is encoded in a bit-packed 64-bit `wr_id`.

The `wr_id` encoding includes:

```text
QP identifier
completion class
buffer slot / sequence information
```

Completion classes include:

```text
control receive
control send
eager receive, when eager benchmark mode is active
eager send, when eager benchmark mode is active
RDMA write
barrier / phase token
```

## 8. Control messages

Control messages use a fixed-size structure.

Target size:

```text
PG_CTRL_MSG_LEN = 64 bytes
```

Structure:

```c
struct pg_ctrl_msg {
    uint32_t tag;
    uint32_t type;
    uint32_t phase;
    uint32_t step;
    uint32_t segment;
    uint32_t micro;
    uint32_t slot;
    uint32_t flags;

    uint64_t len;
    uint64_t addr;

    uint32_t rkey;
    uint32_t credit;

    uint32_t pad[2];
};
```

Control message tag:

```text
PG_TAG = 0x50475244
```

Control message types:

```text
PG_CTRL_RTS
PG_CTRL_CTS
PG_CTRL_DATA_DONE
PG_CTRL_BARRIER
PG_CTRL_EAGER_PAYLOAD
```

Meaning:

```text
RTS:
    sender has a logical segment ready for rendezvous transfer

CTS:
    receiver grants a target region:
        full-segment staging region for Reduce-Scatter
        final recvbuf region for All-Gather

DATA_DONE:
    sender confirms RDMA_WRITE completion:
        per micro-chunk in Reduce-Scatter
        per segment in All-Gather

BARRIER:
    distributed barrier token

EAGER_PAYLOAD:
    header for optional eager benchmark payload SEND
```

Control transport:

```text
Control messages ride the data QP they belong to.

Control for edge rank -> next:
    uses qp_to_next

Control for edge prev -> rank:
    uses qp_from_prev
```

Control receive pools:

```text
Each QP gets its own control receive pool.

PG_CTRL_POOL_DEPTH = 32

Control receive buffers are reposted after consumption.
```

This differs from `bw.c`, where the control pool was never refreshed. Here, pipelined rendezvous and barriers can generate more control traffic, so reposting is required.

Control poll timeout:

```text
PG_CTRL_POLL_TIMEOUT_SEC = 10
```

## 9. Protocol modes

Three compile-time protocol modes are defined:

```text
PG_MODE_RENDEZVOUS_DATA
    control messages eager
    collective payload rendezvous
    default optimized mode

PG_MODE_EAGER_DATA
    control messages eager
    collective payload eager SEND
    benchmark mode for eager vs rendezvous comparison

PG_MODE_AUTO
    payload <= PG_EAGER_THRESHOLD uses eager SEND
    payload > PG_EAGER_THRESHOLD uses rendezvous
```

Default:

```text
PG_MODE_DEFAULT = PG_MODE_RENDEZVOUS_DATA
```

Makefile selector:

```bash
make MODE=rendezvous
make MODE=eager
make MODE=auto
```

## 10. Eager payload benchmark mode

Eager payload mode is compiled in, even though it is not the default payload mode.

Eager payload data uses:

```text
one IBV_WR_SEND with two scatter-gather entries:

SGE 1:
    fixed control header

SGE 2:
    payload
```

Receiver side:

```text
post matching two-SGE receive
copy payload into appropriate work/final buffer
repost eager receive slot
```

Eager receive pool:

```text
PG_EAGER_POOL_DEPTH = 16
```

Eager receive buffer size rule:

```text
eager receive buffer size =
    max(PG_EAGER_THRESHOLD, PG_PIPELINE_CHUNK)
```

This allows forced eager benchmarking to send full pipeline-sized eager packets.

## 11. Ring formulas

The corrected ownership convention is:

```text
rank r owns segment r
```

This makes the public collectives natural.

Let:

```text
N = size
segment_size = count / N
```

Initial version requires:

```text
count % N == 0
```

For `pg_all_reduce()` and `pg_reduce_scatter()`, if:

```text
count % size != 0
```

then return:

```text
PG_ERR_INVAL
```

General remainder support may be added later.

---

## 12. Reduce-Scatter formula

For each step:

```text
for step i = 0 to size - 2:

    send_seg = (rank - i - 1 + size) % size
    recv_seg = (rank - i - 2 + size) % size

    send working[send_seg] to next rank
    receive staging from previous rank
    reduce staging into working[recv_seg]
```

After Reduce-Scatter:

```text
owned = rank
```

---

## 13. All-Gather formula

Before All-Gather steps:

```text
recvbuf[rank] = owned reduced segment
```

Then:

```text
for step i = 0 to size - 2:

    send_origin = (rank - i + size) % size
    recv_origin = (rank - i - 1 + size) % size

    send segment send_origin to next rank
    receive segment recv_origin from previous rank
    place received segment into recvbuf[recv_origin]
```

A shared All-Gather helper is used by:

```text
public pg_all_gather()
internal pg_all_reduce()
```

The helper assumes:

```text
this rank contributes segment rank
```

Count semantics:

```text
pg_all_reduce(sendbuf, recvbuf, count):
    sendbuf has count elements

    sendbuf has count elements per rank
    recvbuf has count * size elements
```

## 16. Work buffer strategy

Two work-buffer modes are defined.

Default:

```text
WORKBUFFER=safe
```

Safe mode:

```text
copy sendbuf into internal work buffer
perform Reduce-Scatter on internal work buffer
sendbuf is not modified
```

Optional performance mode:

```text
WORKBUFFER=inplace
```

In-place mode:

```text
use sendbuf as the Reduce-Scatter work buffer
sendbuf may be modified
```

Makefile selector:

```bash
make WORKBUFFER=safe
make WORKBUFFER=inplace
```

Because in-place mode modifies `sendbuf`, repeated correctness tests and benchmark iterations must refill `sendbuf` before each collective call.

The refill happens outside the timed region.

## 17. Memory registration and caching

User buffers:

```text
MR cache keyed by (pointer, length)
registered on first use
reused if same pointer/length appears again
deregistered at pg_close
```

Assumption:

```text
A cached buffer remains valid until pg_close.
```

Internal buffers:

```text
one cached internal buffer set inside pg_handle
grow-only when a larger collective requires more space
```

Internal buffer set includes:

```text
safe-mode work buffer, when WORKBUFFER=safe
full-segment Reduce-Scatter staging buffer
control/eager staging areas as needed
```

## 18. Reduce-Scatter staging and receive-while-reduce

Reduce-Scatter uses full-segment staging.

For each incoming Reduce-Scatter segment:

```text
Receiver:
    uses a cached internal staging buffer
    grows it if the current segment is larger than before
    sends one CTS granting the whole segment staging region

Sender:
    RDMA_WRITEs each micro-chunk into:
        staging_base + micro_index * PG_PIPELINE_CHUNK

Receiver:
    reduces completed micro-chunks into the working buffer
    network can continue writing later micro-chunks
```

Important detail:

```text
Do not allocate a separate buffer per micro-chunk.
Use one contiguous segment-sized staging buffer.
Each micro-chunk is addressed by offset.
```

DATA_DONE granularity for Reduce-Scatter:

```text
one DATA_DONE per micro-chunk
```

This allows:

```text
NIC writes micro-chunk k+1
while CPU reduces micro-chunk k
```

The design starts with one full-segment staging buffer. Double buffering across segments may be added later if needed.

---

## 19. All-Gather zero-copy

All-Gather uses RDMA Write directly into the final `recvbuf`.

For each All-Gather segment:

```text
Sender:
    sends RTS for one logical segment

Receiver:
    replies with one CTS granting:
        recvbuf + recv_origin * segment_bytes

Sender:
    pipelines RDMA_WRITE micro-chunks directly into that final recvbuf region
    uses windowed selective signaling
    drains all RDMA_WRITEs for the segment
    sends one DATA_DONE for the whole segment
```

DATA_DONE granularity for All-Gather:

```text
one DATA_DONE per logical segment
```

All-Gather has no reduction computation, so micro-chunk DATA_DONE is unnecessary.

---

## 20. RDMA Write signaling strategy

Phase-aware signaling:

```text
Reduce-Scatter:
    each micro-chunk RDMA_WRITE is signaled
    sender sends DATA_DONE per micro-chunk

All-Gather:
    bounded RDMA_WRITE window
    selective signaling
    signal every K writes and always signal the final write
    drain all writes before sending segment DATA_DONE
```

Performance constants:

```text
PG_RDMA_WINDOW          = 32
PG_RDMA_SIGNAL_INTERVAL = 8
```

Bring-up constants:

```text
PG_RDMA_WINDOW          = 1
PG_RDMA_SIGNAL_INTERVAL = 1
```

---

## 21. Pipeline chunking

Pipeline packetization is segment-first:

```text
1. divide the message into size ring segments
2. divide each segment into fixed-size pipeline micro-chunks
3. allow the last micro-chunk of each segment to be smaller
```

Default performance pipeline chunk:

```text
PG_PIPELINE_CHUNK = 256 KiB
```

Bring-up pipeline chunk:

```text
PG_PIPELINE_CHUNK = 64 KiB
```

---

## 22. Barriers

Barriers use a distributed N-1-round ring barrier.

After a rank finishes the phase:

```text
for round = 0 to size - 2:
    send BARRIER(phase, round) to next rank
    receive BARRIER(phase, round) from previous rank
```

Barriers are used:

```text
between Reduce-Scatter and All-Gather inside pg_all_reduce()
in pg_close() before destroying resources
```

This replaces the earlier rank-0-rooted barrier idea.

---

## 23. Progress model

The collective implementation uses a non-blocking progress engine.

The progress engine repeatedly:

```text
polls the shared CQ
processes control receives
advances outgoing RTS/CTS/DATA_DONE state
posts newly granted RDMA_WRITEs
processes completed RDMA_WRITEs
reduces completed Reduce-Scatter micro-chunks
reposts control/eager receive buffers
handles barrier tokens
```

The progress engine must not block on one event while ignoring other progress.

## 28. Correctness test harness

Correctness tests are local and deterministic.

No MPI.

No external tools.

For `PG_INT + PG_SUM`:

```text
For rank r, element i:
    sendbuf[i] = r * count + i
```

Expected all-reduce result:

```text
expected[i] =
    count * size * (size - 1) / 2 + size * i
```

Expected reduce-scatter result for rank r:

```text
rank r receives segment r of the same expected array
```

Expected all-gather result:

```text
recvbuf[origin * count + i] = origin * count + i
```

Correctness matrix:

```text
For pg_all_reduce() and pg_reduce_scatter():
    count values:
        size * 1
        size * 4
        size * 1024
        size * 65536

For pg_all_gather():
    count per rank values:
        1
        4
        1024
        65536

Datatype/operation:
    PG_INT + PG_SUM

Process counts:
    2 and 4

Output:
    PASS/FAIL per test

Return code:
    nonzero on failure
```

If `WORKBUFFER=inplace` is used:

```text
refill sendbuf before each collective call
refill outside timed region
```

## 29. Benchmark harness

Benchmark protocol:

```text
1. allocate sendbuf and recvbuf
2. fill deterministic input
3. run one warmup collective
4. barrier
5. for each timed iteration:
       barrier
       start clock
       pg_all_reduce(...)
       stop clock at local API return
       store time
       barrier
6. report min / median / avg
```

Warmup rules:

```text
Warmup happens before any timed clock starts.
Warmup uses the same buffers, count, datatype, and operation.
Warmup primes the MR cache and internal buffer cache.
A barrier separates warmup from the timed region.
```

Default timed iterations:

```text
PG_BENCH_ITER = 5
```

Benchmark sweep is configurable:

```text
PG_BENCH_MIN_BYTES default = 64 MB
PG_BENCH_MAX_BYTES default = 1 GB
```

Default large sweep, per-process sizes:

```text
64 MB
128 MB
256 MB
512 MB
1 GB
```

The sweep uses powers of two between min and max.

For `PG_INT`:

```text
count = bytes / sizeof(int)
```

If needed, round count up to the next value divisible by `size`.

If a benchmark size cannot be allocated:

```text
print warning
skip that size
continue with remaining sizes
```

Effective bandwidth formula for ring all-reduce:

```text
effective_bytes =
    2 * (size - 1) / size * per_process_bytes

effective_Gbps =
    effective_bytes * 8 / median_time_sec / 1e9
```

Reported fields:

```text
count
per_process_bytes
min_time_us
median_time_us
avg_time_us
effective_Gbps based on median time
```

Benchmark modes are compared by rebuilding:

```bash
make MODE=rendezvous PROFILE=perf
make MODE=eager PROFILE=perf
make MODE=auto PROFILE=perf
```
